## 1. Repository 在两层都有：契约 vs 履约

### 一句话理解

> **同一个 Repository，存在于两个地方：Domain 里的是"契约"，Data 里的是"履约"。**

### 项目文件对照

```
lib/
├── domain/
│   └── repository/
│       └── auth/
│           └── auth.dart                     ← 契约（抽象接口）
│
└── data/
    └── repository/
        └── auth/
            └── auth_repository_impl.dart     ← 履约（具体实现）
```

### 两个文件的本质差异

| | `domain/repository/auth/auth.dart` | `data/repository/auth/auth_repository_impl.dart` |
|---|---|---|
| 内容 | 抽象类，零实现代码 | 具体类，真正执行逻辑 |
| 作用 | 定义"能做什么" | 描述"怎么做" |
| 知道 Firebase 吗 | ❌ 完全不知道 | ✅ 直接调用 |
| 依赖方向 | 被 Data 层依赖 | 依赖 Domain 层 |
| 变化频率 | 极低（业务接口稳定） | 较高（数据源可能替换）|

### 代码层面验证

```dart
// ① Domain 层：只定义接口，没有任何实现
// lib/domain/repository/auth/auth.dart
abstract class AuthRepository {
  Future<Either> signup(CreateUserReq createUserReq);   // 只声明，不实现
  Future<void> signin();
}
```

```dart
// ② Data 层：实现接口，调用 Firebase
// lib/data/repository/auth/auth_repository_impl.dart
import '../../../domain/repository/auth/auth.dart';  // ← Data 依赖 Domain ✅

class AuthRepositoryImpl extends AuthRepository {
  @override
  Future<Either> signup(CreateUserReq createUserReq) async {
    return await sl<AuthFirebaseService>().signup(createUserReq);  // 真正执行
  }
}
```

**import 方向是关键：** Data 层 import Domain 层（外层依赖内层）✅，Domain 层不 import 任何 Data 层的内容。

### 为什么不能把接口和实现放在同一个文件？

如果在 Domain 层同时定义接口和实现：

```dart
// ❌ 错误做法
// Domain 层直接实现，必须 import Firebase
import 'package:firebase_auth/firebase_auth.dart'; // Domain 层知道了 Firebase ❌

class AuthRepository {
  Future<Either> signup(...) async {
    await FirebaseAuth.instance.createUserWithEmailAndPassword(...);
  }
}
```

后果：Domain 层依赖了 Firebase，换数据源就必须改业务代码，分层失去意义。

## 2. 层间访问规则：谁能访问谁

### 标准访问路径（唯一正确路径）

```
Presentation ──▶ UseCase ──▶ Repository接口(Domain) ──▶ RepositoryImpl(Data)
                                                               ↑
                                              Presentation 不应越过这条线
```

### 完整访问规则表

| 访问方向 | 是否允许 | 原因 |
|---|---|---|
| Presentation → UseCase（Domain） | ✅ 允许 | 正确的跨层路径 |
| Presentation → Repository 接口（Domain） | ⚠️ 不推荐 | 应通过 UseCase，不能越级 |
| Presentation → RepositoryImpl（Data） | ❌ 禁止 | 跳过业务层，架构腐化 |
| Presentation → DataSource（Data） | ❌ 禁止 | 跳过两层，严重违规 |
| Data → Domain（实现接口） | ✅ 允许 | 外层依赖内层，方向正确 |
| Domain → Data | ❌ 禁止 | 内层不能依赖外层 |
| Domain → Presentation | ❌ 禁止 | 内层不能依赖外层 |

### 当前项目的现状

当前项目所有代码在同一个 Dart 包里，以下代码**编译器不会报错**，但严重违反架构约定：

```dart
// ❌ 违反架构，但能编译通过
// Presentation 越过 UseCase，直接调 Firebase Service
import 'package:spotify/data/source/auth/auth_firebase_service.dart';

class SignupPage extends StatelessWidget {
  void _signup() async {
    await sl<AuthFirebaseServiceImpl>().signup(...); // 跳过了业务层
  }
}
```

**这正是"逻辑隔离"的局限性**——靠开发纪律约束，没有物理强制。

## 3. 物理分层规划：谁在内谁在外

### 用"稳定性"来决定内外

> **越稳定的代码，越放在内层；越容易变化的代码，越放在外层。**

```
稳定性：高 ◀──────────────────────── 低
         Domain       Data       Presentation
         （核心）     （外层）      （外层）
```

### 依赖关系全景图

```
           ┌──────────────────────────────────────┐
           │            App（组装层）               │
           │    main.dart + service_locator.dart   │
           │       负责 DI 注册，唯一全知道的地方    │
           └──────┬──────────────┬────────────────┘
                  │              │              │
                  ▼              ▼              ▼
        ┌──────────────┐  ┌──────────────┐  ┌──────────────────┐
        │    Domain    │  │     Data     │  │   Presentation   │
        │   （内核）    │  │   （外层）    │  │     （外层）       │
        │              │  │              │  │                  │
        │  entities/   │◀─│  依赖 Domain  │  │  依赖 Domain      │
        │  usecases/   │  │  实现其接口    │  │  调用 UseCase     │
        │  repository/ │  │              │  │                  │
        │  （接口）     │  │  可依赖       │  │  ❌ 不依赖 Data    │
        │              │  │  Firebase/   │  │                  │
        │              │  │  Dio 等SDK   │  │                  │
        └──────────────┘  └──────────────┘  └──────────────────┘
          零外部依赖        依赖 domain 包      依赖 domain 包
                           ❌ 不依赖            ❌ 不依赖
                           presentation         data
```

### 依赖规则一句话总结

> **Data 和 Presentation 都只认识 Domain，互相不认识；App 是唯一全知道的地方，负责把它们粘在一起。**

| 包 | 可以依赖 | 不能依赖 |
|---|---|---|
| Domain | 纯 Dart 工具（dartz 等）| Data、Presentation、Flutter SDK、Firebase |
| Data | Domain | Presentation |
| Presentation | Domain | Data |
| App（组装层） | Domain + Data + Presentation | 无限制 |

## 4. 实现物理隔离的两种方案

### 方案一：Analyzer Lint 规则（低成本，适合小团队）

不拆包，只添加静态分析规则，越层引用时 IDE 直接报红。

**Step 1：** 在 `pubspec.yaml` 加入依赖：

```yaml
dev_dependencies:
  flutter_test:
    sdk: flutter
  flutter_lints: ^6.0.0
  dart_code_metrics: ^5.0.0   # 新增
```

**Step 2：** 在 `analysis_options.yaml` 配置禁止规则：

```yaml
include: package:flutter_lints/flutter.yaml

dart_code_metrics:
  rules:
    - no-prohibited-import:
        forbidden:
          - from: "lib/presentation/**"
            to: "lib/data/repository/**"
            message: "UI 层不能直接访问 Repository 实现，请通过 UseCase"
          - from: "lib/presentation/**"
            to: "lib/data/source/**"
            message: "UI 层不能直接访问 DataSource"
          - from: "lib/domain/**"
            to: "lib/data/**"
            message: "Domain 层不能依赖 Data 层，违反依赖倒置原则"
```

**效果：** 越层 import 时，IDE 画红线报错，`flutter analyze` 命令也会拦截。

---

### 方案二：Melos 多包架构（最彻底，适合中大型团队）

将三层拆成三个独立 Dart Package，通过 `pubspec.yaml` 的依赖声明**编译期物理阻断**越层引用。

#### 目录结构

```
spotify_flutter_demo/          ← monorepo 根目录
├── melos.yaml                 ← Melos 配置
├── packages/
│   ├── domain/                ← Domain 包（纯 Dart，零外部依赖）
│   │   ├── pubspec.yaml
│   │   └── lib/
│   │       ├── entities/
│   │       ├── repositories/  ← 只放接口（抽象类）
│   │       └── usecases/
│   │
│   ├── data/                  ← Data 包（依赖 domain 包）
│   │   ├── pubspec.yaml
│   │   └── lib/
│   │       ├── models/
│   │       ├── repositories/  ← 接口的具体实现
│   │       └── sources/       ← Firebase / 网络请求
│   │
│   └── presentation/          ← UI 包（依赖 domain 包，不依赖 data 包）
│       ├── pubspec.yaml
│       └── lib/
│           └── pages/
│
└── app/                       ← Flutter App（依赖三个包，负责 DI 注册）
    └── pubspec.yaml
```

#### 各包 pubspec.yaml

**Domain 包 — 零外部依赖：**

```yaml
name: domain
dependencies:
  dartz: any          # 可选，函数式工具
  # 🚫 没有 firebase_auth
  # 🚫 没有 flutter SDK
  # 🚫 没有 data 包
  # 🚫 没有 presentation 包
```

**Data 包 — 只依赖 Domain：**

```yaml
name: data
dependencies:
  domain:
    path: ../domain   # ✅ 实现 Domain 的接口
  firebase_auth: any  # ✅ 外部 SDK
  dio: any
  # 🚫 没有 presentation 包
```

**Presentation 包 — 只依赖 Domain，不依赖 Data：**

```yaml
name: presentation
dependencies:
  domain:
    path: ../domain   # ✅ 调用 UseCase
  flutter:
    sdk: flutter
  # 🚫 没有 data 包
  # → 物理上无法 import AuthRepositoryImpl 或 AuthFirebaseServiceImpl
```

**App 包 — 唯一知道全局的组装层：**

```yaml
name: app
dependencies:
  domain:
    path: ../packages/domain
  data:
    path: ../packages/data        # ✅ 用于 DI 注册实现类
  presentation:
    path: ../packages/presentation
  get_it: any
```

#### 物理隔离的效果

```dart
// ❌ 在 presentation 包里写这行 → dart pub 直接报错
// 因为 data 包根本不在 presentation 的 pubspec.yaml 依赖里
import 'package:data/repositories/auth_repository_impl.dart';
// Error: Target of URI doesn't exist 'package:data/...'
```

不需要任何约定和纪律，**物理上就跑不起来**。

---

### 两种方案对比

| 维度 | Lint 规则方案 | Melos 多包方案 |
|---|---|---|
| 改造成本 | 低，加 2 个文件改动 | 高，需要重组项目结构 |
| 隔离强度 | 静态分析拦截，能被忽略 | 编译期物理阻断，无法绕过 |
| 适用场景 | 小团队、学习项目 | 中大型团队、长期维护项目 |
| 团队门槛 | 无额外学习成本 | 需要学习 Melos 工具链 |

## 总结

```
┌─────────────────────────────────────────────────────┐
│                    核心认知                           │
│                                                     │
│  Domain 里的 Repository  =  契约（定义能做什么）        │
│  Data 里的 RepositoryImpl =  履约（描述怎么做）         │
│                                                     │
│  Domain 是内层（最稳定），不依赖任何人                   │
│  Data 和 Presentation 是外层，都只依赖 Domain          │
│  Data 和 Presentation 互相不认识                      │
│  App 是唯一全知道的地方，负责 DI 注册把它们粘在一起        │
└─────────────────────────────────────────────────────┘
```
